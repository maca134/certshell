# SPEC — Web SSH Client (step-ca short-lived certs)

Status: design agreed, not yet implemented.
Scope: **SSH only**. No RDP/VNC/DB/K8s.

---

## 1. Goal

Browser-based SSH terminal with **no stored SSH keys anywhere**.

- Every session mints an ephemeral keypair, signed by step-ca into a short-lived (5–15 min) SSH user certificate.
- Login is a passkey, against the app's own built-in OIDC issuer.
- Target hosts trust the CA, not individual keys.
- Native `ssh` must keep working via `step ssh login` + a jump host.
- Enrolling a new host = paste one snippet generated by the web UI.

### Non-goals

- Multi-user / team RBAC (single user, small trusted group).
- Protocols other than SSH.
- Replacing break-glass access (stays offline, independent of this system).

---

## 2. Architecture

**Single container.** One image, one volume, one process tree. Everything below runs inside it.

```
┌─ web-ssh container ───────────────────────────────────────────┐
│  Bun app (PID 1 under tini, supervises children)              │
│    ├─ HTTP :3000   web UI, terminal WS, enroll API            │
│    ├─ OIDC issuer  oidc-provider + WebAuthn (passkeys)        │
│    ├─ step-ca      child proc, binds 127.0.0.1:9000           │
│    └─ sshd         child proc, :2222, jump host (cert auth)   │
│  /data — step state, SQLite, recordings, sshd config          │
└───────────────────────────────────────────────────────────────┘
        │ passkey login          │ ssh (ephemeral key + cert)
Browser ┘                        └──────────────► Target hosts
                                                       ▲
Native: ssh -J jump@host:2222 ──► sshd (cert auth) ────┘
```

### Components (all in-process or child procs)

| Component | Role | Notes |
|---|---|---|
| **Bun app** | Web UI, terminal, enrollment, host inventory, **OIDC issuer** | Bun + Hono + React, xterm.js |
| **step-ca** | Issues SSH user + host certs | Child proc, loopback-only, never exposed |
| **sshd** | Jump host for native `ssh -J` | Child proc, no shell, TCP forward only |

- No Pocket ID, no separate IdP container, no internal Docker network.
- Issuer = `APP_URL` = `https://ssh.dev.example.com`. One origin, one RP ID, one cookie jar.
- Two-container variant (step-ca split out) retained in Appendix A.

## 3. Auth model

### 3.1 Login — passkeys, self-issued OIDC

- The app is its own OIDC provider: `oidc-provider` (panva) + `@simplewebauthn/server`.
- Passkey-only. No passwords, no SMS, no recovery questions.
- Two OIDC clients registered against itself:
  - `web` — confidential, callback `${APP_URL}/auth/callback` (the browser path).
  - `step-cli` — public/PKCE, callback `http://127.0.0.1:10000` (the native `step ssh login` path).
- step-ca's OIDC provisioner points at `${APP_URL}/.well-known/openid-configuration`, i.e. the same process.

**Why self-issued rather than Google:** step-ca's OIDC provisioner trusts **any** valid token for its client ID. With consumer Gmail, `--domain` is meaningless, so any Google user could obtain a cert with a principal matching their email local part (`root@…`, `admin@…`). A closed, self-hosted issuer removes that class of problem entirely.

### 3.2 User certs

1. Browser session authenticated via passkey → ID token from the in-process issuer.
2. App generates an ed25519 keypair **in memory**.
3. App POSTs to `http://127.0.0.1:9000/1.0/ssh/sign` with the token as OTT.
4. App connects with key + cert, then discards both. TTL 5–15 min.

```ts
const { publicKey, privateKey } = crypto.generateKeyPairSync("ed25519");
const res = await fetch(`${STEP_CA}/1.0/ssh/sign`, {
  method: "POST",
  body: JSON.stringify({
    publicKey: toOpenSSH(publicKey),
    ott: session.idToken,
    certType: "user",
    principals: [session.email],
    validBefore: "15m",
  }),
});
const { crt } = await res.json();
```

- Keep the OIDC round-trip even though issuer and requester share a process. It preserves a single code path for web and native, and keeps step-ca's audit log meaningful.

### 3.3 Host certs — JWK provisioner (`enroll`)

- App holds the `enroll` provisioner password.
- **Must be policy-restricted to host certs only**, and to the host DNS pattern.
- A leaked enroll password must not yield user certs.

### 3.4 Accepted risk of consolidation

- The app is both the identity provider and the cert requester, and holds the CA key password. **A web RCE ⇒ arbitrary certs for any principal.**
- Splitting step-ca out would *not* prevent that, since the app signs the tokens step-ca trusts. It would only protect the CA key material from exfiltration.
- Mitigations (all mandatory, not optional):
  - `AuthorizedPrincipalsFile` on every target lists **full identities**, never bare local parts. This is the real backstop.
  - User cert TTL 5–15 min.
  - Internal-only deployment (VPN/VLAN). No public exposure.
  - Break-glass keys stay offline, unsigned by this CA, with no dependency on this app.
  - Planned: hardware-backed CA key via `step-kms-plugin` — usable in place, not exfiltratable.

## 4. Target host configuration

```
# /etc/ssh/sshd_config.d/50-step-ca.conf
TrustedUserCAKeys        /etc/ssh/step_user_ca.pub
AuthorizedPrincipalsFile /etc/ssh/principals/%u
HostCertificate          /etc/ssh/ssh_host_ed25519_key-cert.pub
```

```
# /etc/ssh/principals/root
mac@example.com          # full identity only — never a bare local part
```

- Existing `authorized_keys` keeps working → no lockout risk during enrollment.
- Host certs let clients skip TOFU: `@cert-authority *.example.com <host CA pubkey>` in `known_hosts`.

### 4.1 Enrollment snippet (generated by the web UI)

CA pubkeys inlined; the only network call uses a one-time, short-expiry token.

```sh
#!/bin/sh
set -eu
CA_PUB='ecdsa-sha2-nistp256 AAAA... step-user-ca'
TOKEN='eyJ...'                     # one-time, 10 min, bound to this host
USER_MAP='root:mac@example.com'

install -d -m 755 /etc/ssh/principals
printf '%s\n' "$CA_PUB" > /etc/ssh/step_user_ca.pub
u=${USER_MAP%%:*}; p=${USER_MAP#*:}
printf '%s\n' "$p" > "/etc/ssh/principals/$u"

curl -fsS -X POST https://ssh.example.com/api/enroll \
  -H "Authorization: Bearer $TOKEN" \
  --data-binary @/etc/ssh/ssh_host_ed25519_key.pub \
  -o /etc/ssh/ssh_host_ed25519_key-cert.pub

cat > /etc/ssh/sshd_config.d/50-step-ca.conf <<EOF
TrustedUserCAKeys /etc/ssh/step_user_ca.pub
AuthorizedPrincipalsFile /etc/ssh/principals/%u
HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub
EOF

sshd -t && { systemctl reload ssh 2>/dev/null || systemctl reload sshd; }
echo "enrolled: $(hostname)"
```

- `/api/enroll` validates the token, signs via the `enroll` JWK provisioner, and registers the host (name, IP, host key fingerprint) in the gateway DB.
- Requires `sshd_config.d` support (Debian 11+ / Ubuntu 20.04+).
- Bake into the Proxmox LXC golden template (CT 9000) for zero-touch enrollment on clone.

## 5. Native SSH path

```
# jump sshd_config
PasswordAuthentication no
KbdInteractiveAuthentication no
TrustedUserCAKeys /etc/ssh/step_user_ca.pub
AuthorizedPrincipalsFile /etc/ssh/principals/%u
AllowUsers jump
PermitTTY no
ForceCommand /bin/false
AllowAgentForwarding no
X11Forwarding no
AllowTcpForwarding yes
PermitOpen *:22
```

```
# client ~/.ssh/config
Host *.lab
  ProxyJump jump@ssh.example.com:2222
```

```sh
step ssh login mac@example.com     # OIDC → cert into ssh-agent
ssh root@web1.lab                  # end-to-end; jump sees only TCP
```

- No session recording on this path (tradeoff for zero custom code).
- sshd runs **inside the same container** (`/data/sshd/sshd_config`, port 2222). The app writes `/data/sshd/principals/jump` and `kill -HUP`s sshd directly — no volume juggling between containers.
- The user CA pubkey is read straight from `/data/step/certs/`, so there is no copy to keep in sync.
- Alternative: skip the jump host entirely and reach targets over VPN — same `step ssh login` flow.

## 6. App implementation notes

- Stack: Bun + Hono + React (house standard), xterm.js front end, WebSocket transport.
- OIDC issuer: `oidc-provider` (panva). Passkeys: `@simplewebauthn/server`. **Verify both run under Bun early** — fall back to Node for the app process if not.
- **Verify early:** `ssh2` (npm) support for OpenSSH *user certificate* client auth is uncertain, and `ssh2` under Bun has had crypto compat gaps.
  - Fallback: spawn system `ssh` in a PTY with key + cert in tmpfs (`0600`), deleted on connect. Gets certs, ProxyJump and modern ciphers for free. `openssh-client` is already in the image.
- App `known_hosts`: `@cert-authority * <host CA>` → verifies targets, no TOFU.
- Session recording: asciinema `.cast` in `/data/recordings` (web path only).
- Exposure-agnostic. Only these env-derived facts about the outside world:

```ts
const config = {
  appUrl: env.APP_URL,                 // WebAuthn RP ID, OIDC issuer, cookie domain, snippet URLs
  trustedProxies: env.TRUSTED_PROXIES, // trust X-Forwarded-Proto/For from the ingress only
  stepCa: env.STEP_CA_URL ?? "http://127.0.0.1:9000",
};
```

- App-level requirements regardless of deployment: `Secure`/`HttpOnly`/`SameSite=Strict` cookies, WS `Origin` check against `APP_URL`, rate limits on login/enroll/token/sign, audit log (logins, cert issuance, sessions), HSTS.
- App must **not** implement IP allowlists or "am I internal?" logic — that belongs to Traefik + VPN ACLs.
- Because issuer and cert-requester share a process, **the audit log is the only record distinguishing them**. Log every sign with subject, principals, TTL and the session that triggered it.

## 7. Deployment

### 7.1 Shape

**Single container.** One image, one volume, one compose service. Rationale and accepted risk in §3.4; two-container variant in Appendix A.

### 7.2 Image

```dockerfile
FROM smallstep/step-ca:latest AS step

FROM oven/bun:1-debian
RUN apt-get update && apt-get install -y --no-install-recommends \
      openssh-server tini ca-certificates && \
    rm -rf /var/lib/apt/lists/* && \
    useradd -M -s /usr/sbin/nologin jump && mkdir -p /run/sshd
COPY --from=step /usr/local/bin/step-ca /usr/local/bin/step /usr/local/bin/
COPY app/ /app
WORKDIR /app
VOLUME /data
EXPOSE 3000 2222
ENTRYPOINT ["tini","--","bun","run","src/main.ts"]
```

`/data` layout:

```
/data
├── step/              # STEPPATH — CA config, keys, db
├── app.sqlite         # hosts, sessions, OIDC clients, audit log
├── sshd/              # sshd_config, host keys, principals/
└── recordings/        # asciinema .cast
```

### 7.3 Process supervision

PID 1 is the Bun app under `tini`. It starts, restarts and reaps the children.

```ts
function startChild(name: string, cmd: string, args: string[]) {
  const run = () => {
    const p = Bun.spawn([cmd, ...args], { stdout: "inherit", stderr: "inherit" });
    p.exited.then(code => {
      log.warn(`${name} exited ${code}; restarting`);
      setTimeout(run, 2000);
    });
    return p;
  };
  return run();
}

startChild("step-ca", "/usr/local/bin/step-ca",
  ["/data/step/config/ca.json", "--password-file", "/run/secrets/step_password"]);
startChild("sshd", "/usr/sbin/sshd",
  ["-D", "-e", "-f", "/data/sshd/sshd_config"]);
```

- Forward SIGTERM/SIGINT to children, then exit. `tini` handles zombie reaping.
- `/healthz` reports child liveness, not just HTTP liveness. `restart: unless-stopped` won't catch a wedged child.
- Wait for step-ca's `/health` before serving sign requests on first boot.

### 7.4 First boot (idempotent, no manual CLI)

```ts
if (!exists("/data/step/config/ca.json")) {
  await $`step ca init --ssh --name ${CA_NAME} --dns 127.0.0.1 --address 127.0.0.1:9000
          --provisioner bootstrap --password-file /run/secrets/step_password
          --remote-management`.env({ STEPPATH: "/data/step" });
}
await startCa();
await ensureProvisioner("web",      { type: "OIDC", clientId: WEB_CLIENT_ID });
await ensureProvisioner("step-cli", { type: "OIDC", clientId: CLI_CLIENT_ID,
                                      listenAddress: ":10000" });
await ensureProvisioner("enroll",   { type: "JWK", sshHostOnly: true });
```

- **Two OIDC clients ⇒ two step-ca OIDC provisioners** — token `aud` must equal the provisioner's client ID.
- Both point at `${APP_URL}/.well-known/openid-configuration`.
- `--dns 127.0.0.1` is deliberate: step-ca is loopback-only and never fronted by Traefik.
- Remove the `bootstrap` provisioner once the OIDC ones exist.

### 7.5 Compose

```yaml
name: web-ssh

services:
  web-ssh:
    build: .
    restart: unless-stopped
    environment:
      APP_URL: https://ssh.dev.example.com
      CA_NAME: "Mac SSH CA"
      STEP_CA_URL: http://127.0.0.1:9000
      TRUSTED_PROXIES: ${INGRESS_IP}   # in-LXC ingress container IP — NOT 10.0.0.3 (see §8.1)
    secrets: [step_password]
    volumes: ["./data:/data"]
    ports: ["2222:2222"]               # bind to the LXC's VLAN IP in prod
    labels:
      traefik.enable: "true"
      traefik.http.routers.webssh.rule: Host(`ssh.dev.example.com`)
      traefik.http.services.webssh.loadbalancer.server.port: "3000"
    networks: [ingress]

  ingress:
    image: traefik:v3
    restart: unless-stopped
    command:
      - --providers.docker=true
      - --providers.docker.exposedbydefault=false
      - --entrypoints.web.address=:80
      - --entrypoints.web.forwardedHeaders.trustedIPs=10.0.0.3
    ports: ["80:80"]
    volumes: ["/var/run/docker.sock:/var/run/docker.sock:ro"]
    networks: [ingress]

secrets:
  step_password: { file: ./secrets/step_password }

networks:
  ingress: {}
```

- `enroll_password` is no longer a file secret — the app generates the JWK provisioner key at first boot and stores it in `/data`.
- Only one bootstrap input is needed out of band: `secrets/step_password`.
- The `ingress` service is dev-convenience only. In prod it can be dropped if the LXC fronts the app directly.

### 7.6 Backup

- One path: `/data`. Stop the container, snapshot, restart. Or rely on PBS at the LXC level, per house pattern.
- `/data/step` contains the CA private keys, encrypted with `step_password`. **Back up the password separately**, or the backup is useless.

### 7.7 What the web UI owns (target: everything except DNS/Traefik/first secret)

| Step | UI? |
|---|---|
| step-ca init + provisioners + policies | ✅ first boot, automatic (§7.4) |
| Admin account + passkey registration | ✅ first-run wizard |
| OIDC clients (`web`, `step-cli`) | ✅ self-registered at first boot |
| Enroll snippets + one-time tokens | ✅ core feature |
| Host list, ACL, principals mapping | ✅ |
| Jump host principals (write file + `kill -HUP sshd`) | ✅ direct, same container |
| Root fingerprint + client `~/.ssh/config` copy block | ✅ |

## 8. Environment

### 8.1 Dev — VERIFIED WORKING

- Dev LXC on edge (Media/Dev VLAN) = `dev-host.example.com`, fronted by Traefik LXC at `10.0.0.3` (`edge.example.com`). Traefik terminates TLS and proxies plain HTTP to `dev-host.example.com`.
- DNS: `dev.example.com` A → `10.0.0.3` (public record, private IP); `*.dev.example.com` CNAME → `dev.example.com`.
- Valid wildcard LE cert via Cloudflare DNS-01. Names resolve publicly but are reachable only over VPN/VLAN.
- Confirmed from inside a container on the dev LXC:
  - `nslookup id.dev.example.com` → CNAME → `10.0.0.3` (resolver `10.0.30.1`)
  - `curl https://dev.example.com/` → `200 verify=0`
  - `curl https://test.dev.example.com/` → `200 verify=0` (subdomain routing + wildcard cert)
  - `nc -zv 10.0.0.3 443` → open
- **Prerequisite:** firewall rule allowing Media/Dev VLAN → `10.0.0.3:443`. Without it, container requests hang. Added and working.
- ⇒ No `extra_hosts`, no split-horizon hacks, no custom trust stores. step-ca can fetch OIDC discovery over the real public URL.

**Ingress: two hops.**

```
browser ──TLS──► edge Traefik (10.0.0.3)  ──plain HTTP:80──►  dev LXC ingress  ──►  container
                 shared prod config                            per-stack, Docker labels
```

**Hop 1 — edge Traefik (existing `dynamic.yml`, no changes needed).**

One router already covers the whole zone:

```yaml
    dev.example.com:
      rule: Host(`dev.example.com`) || Host(`*.dev.example.com`)
      entryPoints: [websecure]
      service: dev.example.com-service      # → http://dev-host.example.com:80
      tls:
        certResolver: letsencrypt
        domains:
          - main: dev.example.com
            sans: ['*.dev.example.com']
```

- **Verified:** `https://test.dev.example.com/` → `200 verify=0` from inside a container on the dev LXC. Wildcard matching and the wildcard cert both work as configured.
- (Documented Traefik v3 behaviour is that `Host()` is exact-match and does not support wildcards. It nonetheless matches subdomains on this instance — possibly version-specific. Don't "fix" it; retest if Traefik is upgraded.)
- **No further edge edits are needed for this project**: everything under `*.dev.example.com` already lands on `dev-host.example.com:80`.

**Hop 2 — in-LXC ingress (part of this stack, see §7.5).**

- Traefik v3 with the Docker provider, `:80`, vhosting by `Host` header to the app container on `:3000`.
- Only one router is needed now: `` Host(`ssh.dev.example.com`) ``. The app is its own issuer, so there's no second hostname.
- Adding a dev subdomain is a label change, with no edit to the shared production config.
- Docker provider is appropriate here (single LXC); the file-provider convention exists for cross-VLAN backends.
- Droppable in prod if the LXC fronts the app directly on `:80`.

**Forwarded headers (two hops ⇒ two trust settings).**

- TLS terminates at hop 1. Both backend legs are plain HTTP, so **no container gets a cert**.
- `X-Forwarded-Proto` is load-bearing: `Secure` cookies, the WebAuthn origin and the OIDC issuer all derive from `APP_URL` + forwarded headers. If it's dropped, login breaks.
- Hop 2 must trust `10.0.0.3` (`forwardedHeaders.trustedIPs`) or it strips the headers from hop 1.
- App `TRUSTED_PROXIES` = the **in-LXC ingress container IP**, not 10.0.0.3. Confirm with `ss -tn` or the gateway's own access log during a request.

### 8.2 Prod

- Same pattern under `ssh.example.com`, internal-only. **One hostname now** — no separate `id.` since the app is its own issuer.
- Own LXC, not shared with other stacks (CA blast radius).
- step-ca binds `127.0.0.1:9000` inside the container and is never routed. Nothing to expose.
- Bind `2222` to the LXC's VLAN/VPN IP, not `0.0.0.0`.

### 8.3 Known failure signatures

- **Hang on connect** = L3/L4, i.e. inter-VLAN firewall, not Traefik. A name with no matching router returns 404 (or a cert error from Traefik's default self-signed cert) and fails fast. Diagnose with `nc -zv <traefik-ip> 443` and the firewall live firewall log, not with router rules.
- Passkeys bind to the RP ID → passkeys registered on `ssh.dev.example.com` will NOT work on `ssh.example.com`. Re-register per environment.
- WebAuthn needs a secure context; self-signed certs are rejected by Chrome even after click-through. Hence the real LE cert in dev.
- **step-ca fetching its own issuer**: the OIDC provisioner resolves `${APP_URL}/.well-known/openid-configuration`, which leaves the container, hits Traefik at 10.0.0.3, and comes back in. Verified reachable (§8.1), but it means a Traefik outage breaks cert issuance even though both parties are in one container.

## 9. Open decisions

- [ ] **Host cert renewal** — long-lived (1y) + re-enroll, vs install `step` on targets + `step ssh renew` from cron. Affects whether the snippet stays curl-only.
- [ ] **Principals mapping** — per-host in the snippet (simple) vs group claim → step-ca SSH template (scales).
- [ ] **`ssh2` vs spawned `ssh`** — decide after the cert-auth spike.
- [ ] **CA key protection** — hardware-backed (YubiKey PIV / TPM via `step-kms-plugin`). The one mitigation that meaningfully offsets §3.4.
- [ ] **step-ca issuer fetch** — leave it going out through Traefik, or short-circuit with a loopback issuer alias. Only matters if Traefik outages become a problem.
- ~~Deploy shape~~ — **decided: single container** (§7.1, risk accepted in §3.4).

## 10. Build order

1. Skeleton container: Bun app + supervised step-ca child; `/healthz` green; first-boot init writes `/data/step`.
2. Self-issued OIDC + passkey registration; first-run wizard. Verify the discovery doc is fetchable **from inside the container** via `${APP_URL}`.
3. Spike: `step ssh login` against the app's own issuer → cert in agent → SSH into one hand-configured target.
4. Web terminal: login → sign → connect → xterm.js.
5. Enroll endpoint + snippet generator + host inventory.
6. sshd child + native jump path.
7. Session recording, audit log, rate limits.
8. Harden: `step-kms-plugin`, provisioner policies, health/restart edge cases.

## 11. Assumptions

- Single user / small trusted group.
- Targets are Linux, OpenSSH ≥ 7.x, with `curl`.
- Internal-only deployment (VPN/VLAN); no public exposure. **This is what makes §3.4 acceptable.**
- Break-glass SSH stays offline, on the VeraCrypt USB, **not** signed by this CA, with no dependency on this app or VPN.
- `oidc-provider` and `@simplewebauthn/server` work under Bun; step-ca binaries are copyable out of the official image. Verify both in step 1.

## Appendix A — two-container variant (rejected)

Split step-ca into its own container on an internal-only network; the app reaches it at `https://step-ca:9000`.

- **Gains:** the CA private key can't be read out of a compromised app process, so post-incident key rotation is meaningful rather than theatre.
- **Does not gain:** protection from forged certs. The app issues the tokens step-ca trusts, so a compromised app mints certs either way.
- **Costs:** second service, internal network, root cert bind-mount, two-stage bootstrap, split backup.
- Revisit if this ever serves more than a small trusted group, or if `step-kms-plugin` turns out not to be workable.
